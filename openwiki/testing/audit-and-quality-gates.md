## `audit_*_test.go`: one file per fixed incident, not per feature

`internal/hub` contains a family of test files named `audit_<topic>_<date>_test.go` (e.g. `audit_dbless_2026_06_15_test.go`), each dedicated to regression-locking a specific past finding rather than being organized around the feature it happens to touch. `audit_dbless_2026_06_15_test.go`'s own header names the finding it locks: `sanitizeCommitMessage`'s UTF-8-boundary truncation must never split a multi-byte rune mid-sequence when trimming to a max length (`TestSanitizeCommitMessageUTF8Boundary`, which deliberately constructs a 70-character Japanese string whose 210-byte length exceeds a 200-byte cap to force the boundary case), and must strip C0 control characters and DEL (while preserving tab/newline) specifically to prevent terminal-escape-sequence injection into git history and WebSocket delivery (`TestSanitizeCommitMessageStripsControl`). Naming the test file after the date and the specific audit finding — rather than folding it into an ordinary `git_commit_test.go` — keeps the connection between "this exact code path" and "this exact incident" traceable years later, the same way `internal/hub/approval_identity.go`, `internal/hub/approval_marker_transcript.go`, and `internal/handoff`'s package docs (see [Approval Detection and Marker System](/openwiki/hub/approval-detection.md) and [Light Orchestration and the Relay Loop](/openwiki/hub/orchestration-relay.md)) each keep their own design rule next to the code that would violate it, rather than in a central document.

## `instrumentation.json`: a ledger against shipping investigative code

`instrumentation.json`'s own header comment states plainly why this ledger exists: the same class of mistake happened three times in a row before it was built — a v0.5.1 debug endpoint that recorded an approval's raw answer text verbatim, later removed in v0.5.2; a v0.5.x wrapper input trace that persisted every keystroke byte unmasked, at world-readable `0644` permissions, with no retention limit, caught only by a pre-release audit; and a v0.6.0 debug endpoint left enabled-by-default all the way until immediately before release. The ledger's own conclusion from those three: writing "remove this once the cause is confirmed" as a code comment does not actually make it get removed — only a machine-checked ledger does. The rules it enforces: any observability code added to the tree must be registered in the same commit that adds it (an unregistered match is blocked outright); an `active` entry has a hard `due` date (a UTC calendar date, not tied to a version number — the ledger notes a version-based scheme was tried first and abandoned because nothing in `release.yml` or the release manual actually advanced the recorded version, so two full releases went out with the same stale version marker); a `gate` (a runtime opt-in condition) is required on every entry, and an "always-on" gate is disallowed as a rule, especially for anything that would persist bytes originating from user input; and a `removed` entry must record `removedIn` and have its files actually verified gone.

`scripts/check-instrumentation.mjs` runs six checks against this ledger: (1) scanning for observability-shaped files/patterns not present in the ledger at all — catching an unregistered piece of investigative code before it can hide; (2) an `active` entry whose `due` date has passed; (3) a `removed` entry whose files have not actually been deleted from the tree — catching the case where only the ledger was edited but the code was left behind; (4) bidirectional consistency between the ledger's active entries and what `web/src/debug/index.ts` actually imports, since either direction of mismatch is a real bug — an import with no ledger entry is an unregistered sink quietly running, while a ledger entry with no corresponding import means the feature believes it is observing something and silently records nothing; (5) that every Go file the ledger lists carries the `//go:build maidebug` build tag, which is the primary guarantee that instrumentation code cannot compile into a release build at all (the secondary guarantee is `scripts/check-artifact-clean.mjs` verifying the *built* release artifact itself); and (6) that every `active` entry carries `artifactNeedles` for the artifact-cleanliness check to search for, and that a `removed` entry's `removedOn` date, if present, is validly formatted.

The ledger separates `files` (a piece of code's own dedicated file, which disappears entirely when the instrumentation is removed) from `sharedFiles` (a shared file like `server.go` the instrumentation only borrows space in, which remains after removal) — the ledger's own comment explains this split exists because collapsing the two into one field forces a bad choice between "registering makes removal impossible to verify" and "removal is checkable but unenforced," and two entries (`ui-input-trace`, `hub-input-trace`) picked the latter option, left `files` empty, and both were consequently forgotten during cleanup before the split existed.

## `check-claude-md.mjs`: a one-way ratchet needs a counter-pressure

`scripts/check-claude-md.mjs` exists because `CLAUDE.md` is the one file loaded in full into every AI session, which makes "put the rule where it will definitely be read" — copying it into `CLAUDE.md` — the locally rational response every time a rule gets violated, and that always-loaded file grew from 129 to 269 lines in five weeks (as of 2026-08-19) purely from seven dated "制定" (established-rule) sections, every one of which duplicated content that already had a canonical home elsewhere (the design doc, a declined-directions ledger, the release manual, `check-instrumentation.mjs`, or the code itself). The script's comment states the structural problem precisely: promoting content *into* `CLAUDE.md` is an established practice, but nothing demotes it back out, so the file can only ever ratchet upward without deliberate counter-pressure — which is what this script provides. It checks three things: the file's total line count against a budget; whether any single section is too long (long prose belongs at its canonical source, with `CLAUDE.md` holding only a pointer); and whether a dated "established" section actually names where its canonical source lives. When the budget is exceeded, the script's prescribed fix order is explicit: first, can the rule be enforced by a machine (a check script or a Go test) so `CLAUDE.md` needs only one line; second, is there a specific file the rule concerns, so the rule can move into that file's own header comment; third, is this actually a yes/no adoption decision, which belongs as one row in `docs/local/reference/reference_declined-directions.md` (see [`CLAUDE.md`](https://github.com/ishizakahiroshi/many-ai-cli/blob/main/CLAUDE.md)'s own design-rule index for the resulting table) rather than prose. Only a rule matching none of those three may keep its full text in `CLAUDE.md` itself.

## CI structure (`.github/workflows/validate.yml`)

The Validate workflow runs several independent jobs rather than one linear script: a **Go** job matrixed across operating systems (build the frontend, then `go build`, `go test`, `go vet`, and verify modules); a dedicated **static-checks** job on Ubuntu that bundles the instrumentation-ledger check, a text-hygiene check, a Docker-build-input-pinning check, a slash-command-definition check, the version-single-source-wiring check (see [Build, Packaging, and Release Pipeline](/openwiki/deployment/build-and-release.md)), a wheel-overlay-registration check, the `CLAUDE.md`-stays-an-index check just described, and an approval-rules-residue check; a `go mod tidy` verification job; a `govulncheck` job; a `gosec` job (scoped to high-severity/high-confidence findings — see [Files and Git Tabs](/openwiki/hub/files-and-git.md) for a concrete example of a deliberate, documented `#nosec` suppression gosec would otherwise flag); a `staticcheck` job; a frontend job (install dependencies, typecheck, build, then run the frontend's own fixture-based `node --test` suite); and a Windows-specific job that checks third-party notices. Splitting these into separate jobs means a failure in one check (say, the instrumentation ledger) is immediately attributable without wading through a single monolithic log covering unrelated concerns.
