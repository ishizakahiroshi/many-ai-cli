> Issue #50 はこのPRでは閉じない。実装・検証が済むまで開いたままにする。

## 目的

`agy -p` を外部エージェントや無人バッチからラップせず、Google公式の未改変
`antigravity-acp` を子プロセスとして起動する ACP準拠クライアントを
`many-ai-cli` に実装する。

## 実装方針（ユーザー承認済み 2026-11-22）

1. 公式・未改変の `antigravity-acp` / `agy acp` バイナリを子プロセス起動する
2. 標準ACPプロトコルで通信する
3. `oauth-personal` の公式ログインフローをそのまま使う
4. トークン抽出・アカウントローテーションを実装しない
5. 無人常駐・放置バッチ・自動ポーリング起動に接続しない
6. Antigravity経由ではGeminiモデルのみ扱う
7. 人間が対話的に操作するCLI／クライアント体験にする

## 検討事項（ユーザー承認済み 2026-11-22）

1. ACPサーバーの起動・終了・異常終了時のライフサイクル設計
2. 対話セッションの履歴、中断、再接続の扱い
3. 非Geminiモデルへのフォールバックを禁止するガード
4. 規約・公式FAQの変更を検知・反映する運用
5. 「個人サブスク枠」と「正規Gemini APIキー」の経路をUI上でも明確に分離する

## 完了条件（ユーザー承認済み 2026-11-22）

1. `agy -p` の外部ラップ実装を廃止または無効化している
2. ACP 4条件を満たす実装になっている
3. 無人バッチからは接続できないことを確認している

## 追加の明確化（ユーザー承認済み 2026-11-22）

### 1. 無人禁止の範囲は Antigravity個人サブスク枠だけ

- #50で禁止するのは、無人バッチから Antigravity の個人サブスク枠へ接続することだけ。
- VPS→ローカルのジョブ連携はOK。ローカルPCの24時間稼働も想定内。

### 2. VPS→ローカルは承認済み案件だけ

- VPS→ローカルに繋ぎに行くのは承認した案件だけ。未承認のジョブはローカルに繋がない。
- ローカルで作業してよいのは、次の両方がそろったときだけ。どちらか一方だけでは作業しない。
  - (1) VPSからの指示がある
  - (2) 承認済みの絞りの印がある

### 3. 認証は最小限のハーネスで、受け取り時の1回だけ

- 確かめるのは「本当にユーザーの指示か」それだけ。確かめられたら、あとはローカルが自立で動く。途中で何回も止めたり、重い仕組みは入れない。
- 長期のベアトークンは使わない。使うなら短期・使い切り・ジョブ紐付けのチケット。

### 4. 別経路での都度確認はしない

- 案件ごとにローカルが別経路で「OKですか？」と聞き直す仕組みは入れない（24時間稼働で詰まるため）。
- 承認は依頼時の一回だけ。その印がVPS経由でローカルまで届く。

### 5. Cloudflare Accessが認証の集約点

- Cloudflareで認証はまとまっている。Cloudflareを通った指示ならそれでOK。
- 追加のベアトークン／チケットのハーネスは不要。

### 6. 依頼の出所に印をつける

- 各依頼に、出所の印をつける。印も案件と一緒にローカルまで届ける。
  - Cloudflare経由のユーザー本人からの直接依頼
  - MCP経由の依頼（その場合は ChatGPTアプリ／Claudeアプリ／その他も分かるようにする）
