# Deskly × many-ai-cli: ローカル司令塔連携（実験計画）

作成日: 2026-10-30。**設計・担当指示のみ。ポーリング・自動起動は未実装、デプロイ禁止。**

## 対応するPR
- Cloudflare/Deskly側: [deskly-private Draft PR #132](https://github.com/ishizakahiroshi/deskly-private/pull/132) (base: `develop`)
- ローカル実行側: この many-ai-cli Draft PR (base: `develop`)
- mmailの検証依頼: [mmail Draft PR #51](https://github.com/kzxb2000/mmail/pull/51)

## 目標と責任分離
- **Desklyが唯一の承認・配信状態・作業台帳**。端末/依頼/実行世代/対象repo/PR/immutable SHAと上限を管理。
- **many-ai-cli Rust Hubがローカル司令塔**。Desklyに対して定期的にアウトバウンドHTTPSで照会し、承認済み依頼のみを取得。既存のセッション・子AI割当・通知・headless実行機構に接続。
- 新たな子AI起動システムや独立した正規タスク台帳を実装しない。既存 `SessionEngine` がセッション/承認の所有者。

## developから確認した既存接続候補
- `rust/src/application/orchestration_program.rs`: conductor/child role・ライフサイクル管理
- `rust/src/orchestration/child_launch.rs`: `SessionEngine`を利用した子セッション起動
- `rust/src/orchestration/headless.rs`: 非対話型プロバイダー実行
- `rust/src/orchestration/relay.rs`: relay records・状態伝達
- `rust/src/orchestration/subagent/`: Claude・Codex・Grok等の子AI起動
- `go/` は移行後の旧実装。新規実装は `rust/` に寄せること。

## ローカルAI担当への作業指示
1. **最初にこのPRとDeskly PR #132のコメント・コードを読んで**、段4 C3の配送契約（認証・generation・start authority・ACK/unknown）の実装状況を照合。重複を禁止する。
2. 現行 `develop` のHub起動・設定・タスク登録・セッション作成経路を追跡して、注入可能な最小の `DesklyPollingAdapter` 境界を設計。生のPRコメントやLLM出力をOSコマンドとして実行しない。
3. 初期ポーリング間隔は**300秒（5分）**。設定変更可能とし、二重起動防止、停止/再起動、タイムアウト、backoff+jitter、off-lineを考慮。取得はローカルからDesklyへの外向きHTTPSのみ。
4. **初期MVPは読むだけ**: 登録端末で承認済みの「対象PRを読んで要約する」を受ける設計。Git checkout/commit/push、テスト自動実行、マージ、本番デプロイはスコープ外。端末側の初回明示承認を要求。
5. **受領済みの正規指示のみ**を実行: repository allowlist、対象immutable SHA、deadline、capability、generation、claim/lease、署名付き/認証済み受領証拠を検証。認証が曖昧なら停止。リプレイ・重複・ACK不明では自動再送せず照合。結果をDesklyの既存段4正規台帳に返す。
6. 小さなtrait/interfaceとモックによる**合成テストから**着手。現在のHubのライフサイクルや他のprovider起動は壊さない。既存CI済み成果を再実行する必要がなければ再試験を要求しない。
7. 確認済みコード・不足するDeskly側API・設計案・合成テストの証拠をこのPRへコメント。コード実装は承認済みの範囲だけ小分けにコミットし、Draftのままレビューへ回す。

## API契約（仮案・**未確定**）
```
poll(registered_device, cursor) -> approved_work[]
claim(request_id, generation, device_id, authority) -> lease | denied
ack(request_id, generation, lease, receipt) -> accepted | unknown
report(request_id, generation, lease, outcome, evidence_ref) -> accepted | held
```
※ 現行DesklyにこれらのHTTP endpointが実装済みとは断定しない。まず正規MCP/HTTP機能の存在を調べて、既存契約を優先すること。

## 非機能/安全条件
- オーナー以外のPRコメントを起動条件にしない。PRコメント自体が作業権限を与えることもない。
- APIトークンは秘密ストアに保存、PR・ログに貼らない。PC側にCloudflare管理権限は不要。
- poll失敗やPC停止ではタスク保持。再起動時は前回のclaimを照合し、不明状態を勝手に再実行しない。
- AIモデルに承認・マージ権限を委譲しない。Deskly側の有効権限が縮小したらローカル側も停止。
- 両PRのレビュー・必要な検証が済むまで既存Hub本番・Deskly Worker/D1に影響を与えない。

## 初期受け入れ条件
- モックで「承認済み１件を一度だけ取得→正規claim→端末の確認→既存Hubへの登録→ACK→PR読取要約→Desklyへ結果登録」を再現。
- 重複poll・異なる端末・期限切れ・SHA更新・拒否・オフライン・ACK不明では二重起動を起こさない。
- PR #51の指示を実際に自動実行したとは主張しない（今は設計のみ）。
