## Entry and scope

`rust-windows-check.yml` runs automatically for relevant pushes to `dots/rust-recovery-resume-3`. It also declares `workflow_dispatch` with fixed choices: `all-tests`, `appserver`, `relay`, `git-turn`, or `conpty`, repeated one, two or three times. Both entry types are restricted to that branch. The input is never interpolated into a shell command; the Python driver validates the allowlist again. Checkout and receipts bind to the event's immutable SHA.

Every choice prepares the four VS runtime DLLs, downloads the locked Go dependencies, builds the real Web assets, runs Python packaging checks, fmt, strict all-target Clippy, and all doctests. The default additionally executes all Rust test targets. Focused choices select the recorded Cargo targets and test-name filters; `conpty` includes the real Hub→wrapper→provider Windows integration test, and `git-turn` includes the real Git and observer budget regressions. Harness inventories and executed counts must agree. Zero matches, ignored-only selections, malformed inventories and any failed repeat fail the check.

The short lane omits optimized release binaries and the license/SBOM collector. Those remain in the full gate. `QUICK-CHECK.json` lists the exact selected/omitted scope and never substitutes for `BUILD-RECEIPT.json` or release acceptance.

## Cache and evidence

All actions use full commit pins. The debug cache contains Cargo registry sources/index/archive cache, Git dependency object cache, and only host/Windows debug targets. It contains no Cargo credentials/config or release outputs. The restore prefix identifies this lane and branch, runner image, target, Rust version, debug/incremental flags and the digest of build/driver/workflow inputs; the full key also identifies the source SHA. A missing image identity disables caching. Cache failures do not skip validation, and test failures may still save compiled dependencies.

Every attempt recomputes source identity, tool versions, generated assets, runtime receipt and validation results. Restored artifacts do not count as test results. The final source check allows only files generated by this invocation and rejects tracked changes or unrelated untracked files. Workflow setup evidence is written after that check, so it cannot make the initial checkout dirty. Artifacts include source SHA, run ID and attempt, preserving separate failures and reruns. `WORKFLOW-CONTEXT.json` records requested source, setup/cache outcomes and first-step timing; actual `QUICK-CHECK.json` source identity is verified separately.

Measure cold and warm attempts using Actions job `started_at`→`completed_at`, including setup and upload, and record queue delay separately if relevant. A warm claim requires the actual matched cache key; an attempted restore alone is insufficient. The workflow's first-step interval is supplemental and excludes final upload/job overhead.
