# V06 supplement: SQLite 3.53.2 reachability and Cargo 1.90.0

> 最終更新: 2026-10-05(月) 23:17:48 UTC

## Result and scope

**Keep V06 pending.** The checked-in Rust code and supplied four-target build records select bundled SQLite 3.53.2. Later SQLite fixes include paths that this application uses when opening existing databases, searching FTS5 indexes, and performing maintenance. There is no demonstrated remote SQL-injection path or reproduced exploit in this review, but parameter binding and trial-directory checks do not establish that crafted database files or journals are safe to open.

Cargo 1.90.0 also predates several officially documented toolchain security fixes. The previous three-CVE paragraph should be expanded: the Rust 1.94.1 release includes both tar CVEs, and Rust 1.96.1 includes three libssh2 CVEs. The current crates.io-only dependency graph narrows the documented attack prerequisites. It does not patch Cargo, prove that build environments have no registry overrides, or establish a safe credential-bearing release process.

Review date: 2026-10-05 UTC. Source: `4dc961ce600d12aa0911e5a9620e50411ab13d9f`. Read-only examination covered the current source, existing V06/V03 reports, four supplied `4dc961ce` CI ZIPs, and current upstream primary sources. No package installation, build, application execution, malformed-input execution, real-data/credential access, dependency change, repository edit, Git mutation, publication, or release-workflow change was performed. This is an assessment supplement, not cutover or dependency-upgrade approval.

## 2. Actual database and SQL reachability

### Database opening and trust boundary

The production path derives `any-ai-cli.db` from the configured log directory (`rust/src/config/paths.rs:140–182,283–303`). Startup chooses that path, obtains the database-owner lease and opens storage (`rust/src/application/main_program/serve.rs:155–190`). Storage creates an empty database only when absent; `AlreadyExists` is accepted, so existing bytes are intentionally read (`rust/src/storage/repository.rs:49–87`). Unix setup holds the file and applies mode 0600 before releasing the setup handle. These are ownership/path controls, not database-content authentication.

`rust/src/storage/schema.rs:4–42` opens the file using rusqlite defaults, adding `SQLITE_OPEN_NOFOLLOW` in trial mode. The [pinned defaults](https://github.com/rusqlite/rusqlite/blob/e88f112bef7899234a497baed5cc3c3d553deeb8/src/lib.rs#L1255) are read/write, create, no-mutex and URI. Initialization then runs pragmas including `journal_mode=WAL`, the additive base schema and missing-column additions. The application serializes its single connection behind a Rust mutex (`rust/src/storage/mod.rs:89–127`).

The critical distinction is that **WAL configuration is requested after opening an existing database**. A pre-existing rollback journal can be considered during early database access before conversion to WAL. The application does not need to issue `ATTACH` itself to encounter an attacker-supplied hot journal that contains a super-journal pointer. SQLite's VFS performs those operations internally. The freshly retrieved [3.53.2 pager source](https://github.com/sqlite/sqlite/blob/ccc132c5be20ab5c755c97a08d06b1b592fef330/src/pager.c#L2534) contains the pre-fix `pager_delsuper` logic and unlink at line 2622, without the subsequently added filename/membership checks.

Trial path checks enumerate the database, `-wal`, `-shm` and `.reset-pending` (`rust/src/storage/repository.rs:32–47`). They do not enumerate `-journal` or super-journal paths encoded inside a journal. `SQLITE_OPEN_NOFOLLOW` and the held application directory do not by themselves constrain every pathname interpreted by the SQLite VFS. This is a concrete **source-reachable concern under a crafted DB/journal prerequisite**, not a demonstrated escape or proof that any current real database is malicious. No evidence here shows an unauthenticated remote party can place those files.

### Queries and FTS

The router applies its preflight before session read routes (`rust/src/hub/router.rs:1184–1227`). `/api/session-search` passes `q` to the existing store (`rust/src/hub/session_routes.rs:121–132`), without choosing a database file or SQL statement.

Search uses a fixed query, binds its values, quotes each FTS term and joins terms with `AND`; the selected FTS query invokes `MATCH`, `snippet(...)` and rank ordering (`rust/src/storage/repository.rs:747–805`). This narrows arbitrary SQL and FTS-expression injection. It still makes SQLite traverse whatever FTS index pages are in the opened database. The LIKE fallback only handles returned SQLite errors (`repository.rs:397–409`); it cannot recover from native memory corruption or a process crash.

Normal writes also use FTS5. `insert_message` inserts into messages and `messages_fts` with bound parameters (`repository.rs:640–660`). Session replacement, pruning and reset delete FTS rows (`repository.rs:231–233`; `rust/src/storage/history.rs:49–60,90–105,177–179`). Maintenance invokes incremental vacuum, checkpoint and full vacuum (`history.rs:26–27,132–136`). These paths matter for corrupt-record and secure-delete fixes; only reviewing searches would be incomplete.

The authored FTS table is an external-content table with two text columns and `content='messages', content_rowid='id'` (`schema.rs:42`), not a contentless-delete table, a `detail=columns` table or a custom tokenizer/auxiliary function setup. `CREATE ... IF NOT EXISTS` and additive migrations do not verify that an existing schema matches those definitions or strip extra triggers. A crafted database can contain persisted schema/configuration that clean application-created databases do not have. In the exact [3.53.2 FTS configuration source](https://github.com/sqlite/sqlite/blob/ccc132c5be20ab5c755c97a08d06b1b592fef330/ext/fts5/fts5_config.c#L1019), `secure-delete` sets `bSecureDelete`, and configuration is read from `%_config` beginning at line 1052. Thus the absence of an application setter alone does not exclude an existing database's secure-delete setting. Feature-specific exclusions below distinguish **normal authored schema** from **arbitrary supplied database**.

### Controls actually present and absent

Busy timeouts, progress callbacks, a serialized connection, trial path checks, private directory/file operations and graceful handling of returned initialization errors are present (`schema.rs:22–46,66–67`; `mod.rs:89–127`; `serve.rs:177–202`). They are useful operational controls; none proves memory-safety of the bundled C parser.

The reviewed production source has no application call to SQLite backup/deserialize APIs, no authored `ATTACH`, FTS `integrity-check`, RTree table, JSON SQL function, custom FTS auxiliary API, or runtime extension-loading enablement. The authorizer in `schema.rs:110` is inside `#[cfg(test)]`, not a production guard. No production `DbConfig`/`trusted_schema`/defensive-mode configuration was found. JSON data is serialized/deserialized by serde_json and stored as text; naming a column `payload_json` does not itself invoke SQLite JSONB.

The compiled C extension-loading capability is distinct from enabling it for a connection. Do not infer active extension execution merely from `SQLITE_ENABLE_LOAD_EXTENSION=1`, or claim the C capability was compiled out because rusqlite's wrapper feature was unselected.

### Later development fix and CVE interpretation

The official mirror also contains an **August 11, 2026** [FTS5 secure-delete bounds correction](https://github.com/sqlite/sqlite/commit/d9de6eedbe918c074c7556400fa21df5960704d9), Fossil `9cd4f9e9205c5a5096388397a39349db9ff5377d19095c6b20388ff799969c31`. It changes term-index accumulation and checks an offset before rewriting a page. The vulnerable pre-fix structure is independently present in the freshly retrieved [3.53.2 FTS5 source at lines 5504–5523](https://github.com/sqlite/sqlite/blob/ccc132c5be20ab5c755c97a08d06b1b592fef330/ext/fts5/fts5_index.c#L5504), file Git blob `ce553370224338b17ffd055911b0792d8114fdf3`, and [3.53.4 source at lines 5515–5534](https://github.com/sqlite/sqlite/blob/b09c88c14082339b66c7b7158d609a771e64ca69/ext/fts5/fts5_index.c#L5515), blob `b683e2198d4db263eb4e7f4fefd1ed8e8e8fc74d`. Applicability is not inferred solely from the patch's date. No later released-version inclusion was established in this review; do not recommend 3.53.4 as a complete resolution of every currently known malformed-DB issue. The same conditional secure-delete/crafted-database boundary applies, without a local reproducer.

[SQLite's current CVE page](https://sqlite.org/cves.html), last updated August 1, identifies CVE-2026-11822 and CVE-2026-11824 as the same FTS5 issue fixed in 3.53.2. They are not evidence that this selected 3.53.2 source lacks that fix. Conversely, that CVE table and a RustSec wrapper lookup do not exhaust later SQLite check-ins. [SQLite's security guidance](https://sqlite.org/security.html) explicitly treats untrusted SQL and malicious database files as separate input surfaces. Defensive mode, limits and schema restrictions should be evaluated as compatibility-sensitive defense in depth; they are not substitutes for native bounds fixes or an OS containment boundary.
