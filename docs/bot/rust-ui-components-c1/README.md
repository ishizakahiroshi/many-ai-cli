## 調査手順

1. `CLAUDE.md`、`CLAUDE/development.md`、`CLAUDE/operations.md` を読む。仕様は公開READMEと調査SHAのsource。`.omitnix/index.json` がある場合は最初に索引を確認するが、generated.commitとの相違や解析不可を記録し、sourceで確かめる。生成物を手修正しない。
2. `web/src/index.html`、`web/src/styles.css`、`web/src/styles/*.css`、`web/src/app/*.ts`、`web/src/i18n/*.json` の対象リストを固定する。過去の計数を流用せず、このSHAの値を再測定する。
3. 画面の名簿を作る。メイン、各サイドバー・タブ、モーダル・設定、モバイル、分離表示について、入口・描画元・適用CSSを対応づける。DOM部品と画面を取り違えず、未追跡の入口は理由を記す。
4. 五つの軸（色と段階、ボタン、モーダルと重なり面、アイコン、流用の仕組み）で実在する実装を分類する。入力欄・フォント・hover・active・disabled・focus-visibleも対象。種類はクラス名の数ではなく、背景・枠・文字・状態色・高さ・余白・角丸や、枠・幅・閉じ方・暗幕の組で数える。CSSのcascade、テーマ、メディア条件、継承を示し、静的に最終値を確定できない項目は未確認とする。
5. `settings.ts` の `appConfirmShutdown` を入口に、停止モーダルの描画と呼出元、`confirm-dialog` / `confirm-btn` / `model-picker-overlay` のスタイル、wheel除外を追う。Esc・外側クリック・Enter・初期focus、外部公開停止checkbox、キャンセルと二つの停止操作、後始末を名簿にする。今回その挙動は変更しない。
6. 実際に値が異なる箇所はファイル・行・値を少なくとも二例並べる。「source上の相違」「意図した役割の差」「画面での確認待ち」を分ける。数や色の値の違いだけから、実画面が乱れていると断定しない。
7. 同じ基準SHAを別担当が読み、名簿の漏れ、計数再現性、CSS条件の無視、既存共通部品の見落とし、未確認を合格扱いする記述をレビューする。指摘を直した後は修正SHAで再確認する。
