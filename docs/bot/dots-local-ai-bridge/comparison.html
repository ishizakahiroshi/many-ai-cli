MCP EventsとSocketを同じ課題で比べる

MCP EventsとSlack Socketの両方を比較し、主経路と補助経路を選ぶ。
MCP Eventsにはdots対応の公開根拠がある。登録・権限・実往復は未確認。先にMCPが成功してもSocketの同課題比較を続ける。[O1]

Socket受信自体にはSlack用の公開受信口が不要。一方、別Botの投稿でdotsが起動するかは未確認。Slackの配送成功や本人投稿の成功を、その証明にしない。[S8]

公式仕様 公開された能力 ソース確認 基準コードの読取 未確認 本環境の権限・疎通・自動再開

調査上の評価優先度は維持し、採用手順は複数候補比較へ変更。8事例と採用条件を参照。実践報告と本環境の実測を区別する。

本C1は文書のみ。通信実装、app／scope／webhook新設、外部試験投稿、HubやAIの起動、配備は未実施。PC電源断中はどの方式でもそのPCのAIは動かず、常時中継が依頼を保存して復帰を待つ。

調査上の評価優先度と横断比較

順位は調査上の優先度。C2はMCP/Socketの両方を評価し、最初の成功では終えない。GitHubはまず記録用、HTTPは条件により追加する。低遅延は期待特性で、実測値はない。狭い画面では表を横へスクロールできる。

順位・方式公開口 / 常駐PC停止と保存導入・運用 / 遅延最大の未確認ゲート
1　MCP Events中継HTTPS / 中継＋PC受信中継受理分をqueue保持高 / event駆動plugin登録・購読・同じjob再開

PC停止中の受付を優先するなら、Slack案ではHTTP＋常時queueをSocket localより先に評価する。Socketもcloud常駐＋queueにすれば耐性を追加できる。違いの本質は、受信・保存をPCから分離するかにある。

既存Hubはどこまでできるか

ソース確認 定義済みroutineを認証付きHTTPで開始し、新しいAI sessionを起動する経路はある。外部eventから既存AI会話を自動再開する完成済みbridgeではない。

  • POST /api/routines/<id>/runs はrequest_idを受ける。prompt・cwd・providerは保存済定義から使う。
  • Hubはloopback bind。token・Host・Origin等の既存guardを維持し、ローカルbridgeが呼ぶ。Hub tokenを中継やSlackへ渡さない。
  • 同routineがactiveなら新request_idも既存runへ永続aliasされる。そのIDは終了後も同じrunへ戻るため、bridgeはactive中にdispatchしない。衝突したら対応を照合して止め、盲目的に再試行しない。
  • 承認待ちと未確認終了を区別する。再起動時の逃したscheduleはskipし、失われたAIのpromptを勝手に再実行しない。
  • Rust移植版との統合、本人PCのCLI認証・cwd・起動権限・実動はローカル確認待ち。

評価優先 1

専用HTTP / MCP 通知口

推奨は MCP tools ＋ MCP Events ＋ 永続キュー

公式仕様あり・一往復未実測

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. MCP tool → 専用中継で保存
  3. PC受信プログラムが取得
  4. Hub認証 → ローカルAIを必要時だけ起動

復路　ローカルAI → dots → 完了受信

  1. ローカルAIの依頼・回答
  2. 中継が保存 → MCP Events callback
  3. dotsの購読チャットで処理・再開
  4. 完了をtoolで中継 → PCが受信
利点
dotsでのイベント反応に公開製品根拠がある。Slack bot同士の受信条件に依存せず、構造化IDと状態を扱いやすい。
弱点
新しいplugin・認証・常時中継・購読管理が必要。一般のHTTP POSTやMCP通知だけではこの経路にならない。
設定と権限
認証付きMCP 2.0 endpoint、toolsとevents/list・subscribe・unsubscribe、callback検証、購読永続化。公開口は中継側だけ。本人のplugin接続・イベントtask許可をC2前に確認。
PC停止と復旧
中継が受付済みの依頼はPC停止中も保持可能。PC再接続までローカルAIは起動しない。期限切れ・順序逆転・重複はアプリ側で処理。
費用と負荷
導入・運用は高め。中継compute/storageとAIの実行分を分離。通知を受けただけで追加AIを無制限に起こさない。
条件と注意
公開仕様は対応を確認。本アカウントでのplugin登録可否、実際の購読、質問後の同じjobへの再開、Hubとの往復は未確認。

評価優先 2

Slack Events API / Socket Mode

PCから外向きWebSocketで受ける

配送仕様あり・dots受信ゲート未確認

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. 専用Slack会話に保存
  3. Socket受信プログラムがACK・保存
  4. Hub認証 → ローカルAIを起動

復路　ローカルAI → dots → 完了受信

  1. ローカルAIの依頼・回答
  2. chat.postMessage → 同一thread
  3. dotsの受信・再開条件は未確認
  4. 完了 → Slack → Socket受信
利点
公開HTTP入口不要。PCが稼働する小さな試作に向く。Slack会話を人も読める。
弱点
別Bot投稿でdotsが起動するかが最大のゲート。接続refreshと欠落補完が必要。Socketは保存装置ではない。
設定と権限
bridge app、app-level connections:write、参加会話のhistory scope、chat:write。botの会話参加とdotsとの共存。ローカル受信プロセスは常駐。
PC停止と復旧
PC上だけのreceiverは停止中受信不可。再接続＝全件replayの保証は確認できず、履歴との差分照合が必要。cloud receiver＋queueなら停止耐性を追加できる。
費用と負荷
初期は中、常駐PCと再接続運用が必要。Slack契約・app枠・LLM枠は別。API無料／LLM無制限とは断定しない。
条件と注意
Slackのbot event表現は確認。dotsが別Botの本文を依頼として扱うか、mentionなしthread返信の回収、補完可能期間は未確認。

評価優先 3

Slack HTTP Events ＋中継

常時受信と永続化をPCから切り離す

配送仕様あり・中継未構築

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. Slack保存 → HTTPS Events
  3. 中継が署名検証・queue保存・ACK
  4. PC受信 → Hub認証 → ローカルAI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIの依頼・回答
  2. chat.postMessage → 同一thread
  3. dots再開はSocket案と同じ未確認
  4. 完了 → 中継保存 → PC受信
利点
PC停止中の受付を維持しやすい。永続queueで受理後の再試行・監査・dead-letterを設計できる。
弱点
HTTPS公開口、署名、ストレージ、監視が増える。Socketから変えてもdotsのbot拒否条件は解決しない。
設定と権限
Slack app/event設定、signing secret管理、中継HTTPS、queueとPC outbound取得。scopeはSocket案と会話種別に応じた同等範囲。
PC停止と復旧
中継受理分を保持し、PC復帰時に取得。Slackの未配送分は別問題。PCへのtunnelだけでは停止耐性は得られない。
費用と負荷
導入・運用は高。queue保持量・egress・監視費とSlack/AI契約が別。低遅延候補だが実測値なし。
条件と注意
HTTPは3秒以内ACK、通常最大3回retry。Delayed Eventsの24時間毎時retryもbest effortで永続保証ではない。

評価優先 4

GitHub Webhook

Issue / PR会話を記録の正本にする

配送仕様あり・dotsのevent購読未確認

往路　dots → ローカルAI

  1. dots が質問・停止・完了をcomment
  2. GitHubが保存 → issue_comment
  3. HTTPS中継が検証・queue保存
  4. PC受信 → Hub認証 → ローカルAI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIが依頼・回答comment
  2. GitHub保存 → dots側のevent購読等
  3. dotsの起動・再開は別途必要
  4. 完了comment → webhook → PC
利点
コメントURL・IDが証跡になる。Slackの会話範囲に左右されず、コード案件と対応づけやすい。
弱点
GitHub webhook自体はdotsを起こさない。接続済pluginが対象commentを起動条件にできるか未確認。新規受信口と管理権限も必要。
設定と権限
repo webhook管理権限、またはGitHub App Issues:read購読。comment読書きはIssuesまたはPull requests権限。HTTPS中継、署名secret、10秒以内2xx。
PC停止と復旧
受理済queueとGitHubコメントから復旧。GitHubは失敗配信を自動再送しないため、再配信・差分照合を設計する。
費用と負荷
中～高。中継運用とAPI上限あり。Actionsを中継にする場合は別の実行枠・設計が必要で本案に暗黙追加しない。
条件と注意
issue_commentはPR会話コメントも対象。inline review commentは別event。gh webhook forwardは開発・試験専用でproduction非対応。

評価優先 5

GitHub 軽量ポーリング

AIを起こさない小さな差分取得プロセス

差分取得仕様あり・自動往復未確認

往路　dots → ローカルAI

  1. dots が質問・停止・完了comment
  2. GitHubに保存
  3. PCが対象Issueの差分を定期GET
  4. 新しいjobのみ保存 → Hub → AI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIが依頼・回答comment
  2. GitHubに保存
  3. dots側の許可済起動経路が必要
  4. 完了commentを次回GETで回収
利点
公開受信口不要。GitHubに残る履歴からPC復帰後に追いつける。限定された案件では実装が小さい。
弱点
検知は巡回間隔分遅れる。PC側pollだけではdotsを起こせない。削除・非公開化・権限変更で復元できない。
設定と権限
単一Issue/PRのcomments API、最小read/write権限、ETag/If-Modified-Since、ページング、comment IDのwatermark、429/403 backoff。
PC停止と復旧
停止中はGETも実行も不可。復帰後の可視コメントを照合する。編集の扱いと古い未処理jobのTTLを決める。
費用と負荷
初期低、運用中。通常認証5000 requests/h。認証付き304はprimary枠を消費しないがsecondary制限等は残る。
条件と注意
GitHub公式はwebhook優先。これは公開口等を使えない場合の代替。dots側を毎回AI巡回させる設計は採用しない。

根拠：G5 / G6 / G7

評価優先 6

Slack 軽量ポーリング

小さな専用会話の補完・代替

取得仕様あり・対象権限とdots受信未確認

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. Slack会話とthreadに保存
  3. PCがhistory＋対象repliesをGET
  4. 新しいjobのみ保存 → Hub → AI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIが依頼・回答を投稿
  2. Slack同一threadに保存
  3. dotsの別Bot受信条件は共通
  4. 完了をhistory/repliesで回収
利点
公開受信口やSocket接続維持が不要。既存会話の補完には使いやすい。
弱点
historyだけでは古い親への返信を拾えない。保持期限・app分類・会話数で復旧と遅延が変わる。bot拒否を回避できない。
設定と権限
historyとrepliesの対象を固定し、会話種別のhistory scope＋chat:write。thread_ts・ts・pagination・取得watermarkを保存。
PC停止と復旧
復帰後にアクセス可能で保持中の履歴のみ補完。削除済／保持期限外は復元保証なし。本人とdotsの既存DMを第三Botが読めると仮定しない。
費用と負荷
内部専用appは現行Tier 3（50+回/分）。Marketplace外の新規商用配布等は1回/分・15件の制限対象。method×workspace×appで評価。
条件と注意
対象app分類、tokenでの実際のthread可視性を確認。一律user token必須／全app1回毎分とは断定しない。

C2は両候補の比較と複数入口の検収

設計のみ。実装・設定・起動・外部送信・接続実験は未実施。旧「最初の成功で採用」は固定追加指示で置き換えた。MCP EventsとSocketで同じ二課題を測り、必要ならSlack HTTPを追加する。

入口が二つでも案件と起動は一つ

  1. MCP tool / Slack受信
  2. 認証・識別子検査 → 共通inbox/job queue
  3. 単一PC worker → Hubの同じrequest_id/run
  4. 共通outbox → 選択経路 → dots同job続行

relayとDBはPC外の常時サービス、Socket receiverは最小比較ではPC、Hubはloopback。MCP用HTTPSは共通relayに必要。PC停止中はSocket受信も止まるため、受理済みqueueとSlack上の未受信を分ける。HTTPを追加するときは受信・投稿をrelay側へ置く。

  1. 本人がM/Sの利用可否、専用会話・plugin、権限、PC/Hub/CLI/cwd、費用上限を確認。
  2. color課題：「色を質問し、固定回答『青』で完了」をMとSでそれぞれ評価。
  3. recovery課題：同じ質問/回答を二度適用せず、停止状態と経路切替を記録。M/S双方で評価。
  4. 依頼→dots質問→保存→新規AI→回答→dots続行→完了回収の7区間を相関。片方向・ACKだけは部分成立。
  5. 共通queue・認証・PC・dots側条件の障害を切り分け、主経路・補助/手動復旧・GitHub記録を本人が選ぶ。

候補間は同じfixtureで異なるjob_id。一つのjobを別入口へ切り替えるときはjob_idとlaunch request_idを維持する。二経路の同じ報告は共通logical_message_id、transport別source_event_id、payload hashで照合する。

候補別の最小構成・本人操作・撤収

MCP Events：認証MCP＋永続queue＋PC worker。本人がPluginsの追加可否と専用接続を確認し、tools/eventsを検出して対象dotで購読。callback検証と2xx、dotsの処理、完了toolを別記録。試験後unsubscribeし一時接続を必要範囲だけ戻す。中継/DBとAI利用枠の費用を確認。

Socket：専用Slack会話＋PC receiver＋同じqueue/worker。本人がappのSocket Mode、connections:write、選んだ会話history、chat:write、mention権限、両app参加を設定。Botの受理は未確認。終了時receiver停止・台帳照合・一時scopeを撤収。PCとAI枠を計上。

Slack HTTP：PC停止中受付やSocket固有制約が必要な場合だけ。本人がRequest URL/署名設定、Socket旧設定を記録。常時relayで署名検証・3秒ACK・保存。試験後URL/購読を戻し、保留outboxを残して照合。Bot拒否はtransport変更で直ると仮定しない。

GitHub：固定指示・成果・レビュー・検収記録が基本。Webhook/poll追加は実益とdots起動条件が明確なときだけ。全7方式を実装・常設する計画ではない。

複数入口と復旧で確かめること

共有状態と二重実行を確かめる検査
試験合格に必要な証拠不成立・未確認の扱い
同一報告が二経路から到着意味イベント・Hub run・回答・完了が各1件同IDで本文が違えば競合停止
遅延・順序逆転古いsequenceで状態を巻き戻さず、前提を欠く完了は保留順序を推測して完了扱いしない
自己返信ループoutbox由来のechoを除外、余分なAI起動0任意Bot許可やdot返信の一律除外で代用しない
主経路停止と元経路復帰同jobで補助へ移管、旧epochの後着を実行しない別dots会話の同job続行が不明なら自動切替不可

Hub共通ゲートと追加実装の境界

既存の起動POSTはrequest_idだけを受け、動的promptは渡せない。新規提案のworkerが専用cwdの合成mailboxを用意し、固定manual routineから新規AIを起動する。新規AIへ現在の会話の認証やconnectorを継承できるとは仮定しない。

launch intentをPOST前に保存。active中はdispatchせず、応答喪失は既存run一覧/詳細を照合する。別runへの永続aliasや未確認状態を別request_idで隠さない。live tool待ち・既存session resume・fresh run・dots同job続行は別物。既存session案にはTUI/bridgeの単一writerが必要。

提案ファイルはcmd/dots-bridge-c2/main.go、internal/dotsbridge配下のprotocol/store/MCP/Slack/Hub adapterとfake tests。まだ存在せず、既存Hub APIとは分ける。既存SQLite依存を再利用する案で、#3 Rustの作業やHub既存DBへ手を入れない。
