既存Hubはどこまでできるか

ソース確認 定義済みroutineを認証付きHTTPで開始し、新しいAI sessionを起動する経路はある。外部eventから既存AI会話を自動再開する完成済みbridgeではない。

  • POST /api/routines/<id>/runs はrequest_idを受ける。prompt・cwd・providerは保存済定義から使う。
  • Hubはloopback bind。token・Host・Origin等の既存guardを維持し、ローカルbridgeが呼ぶ。Hub tokenを中継やSlackへ渡さない。
  • 同routineがactiveなら新request_idも既存runへ永続aliasされる。そのIDは終了後も同じrunへ戻るため、bridgeはactive中にdispatchしない。衝突したら対応を照合して止め、盲目的に再試行しない。
  • 承認待ちと未確認終了を区別する。再起動時の逃したscheduleはskipし、失われたAIのpromptを勝手に再実行しない。
  • Rust移植版との統合、本人PCのCLI認証・cwd・起動権限・実動はローカル確認待ち。

検証 1位

専用HTTP / MCP 通知口

推奨は MCP tools ＋ MCP Events ＋ 永続キュー

公式仕様あり・一往復未実測

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. MCP tool → 専用中継で保存
  3. PC受信プログラムが取得
  4. Hub認証 → ローカルAIを必要時だけ起動

復路　ローカルAI → dots → 完了受信

  1. ローカルAIの依頼・回答
  2. 中継が保存 → MCP Events callback
  3. dotsの購読チャットで処理・再開
  4. 完了をtoolで中継 → PCが受信
利点
dotsでのイベント反応に公開製品根拠がある。Slack bot同士の受信条件に依存せず、構造化IDと状態を扱いやすい。
弱点
新しいplugin・認証・常時中継・購読管理が必要。一般のHTTP POSTやMCP通知だけではこの経路にならない。
設定と権限
認証付きMCP 2.0 endpoint、toolsとevents/list・subscribe・unsubscribe、callback検証、購読永続化。公開口は中継側だけ。本人のplugin接続・イベントtask許可をC2前に確認。
PC停止と復旧
中継が受付済みの依頼はPC停止中も保持可能。PC再接続までローカルAIは起動しない。期限切れ・順序逆転・重複はアプリ側で処理。
費用と負荷
導入・運用は高め。中継compute/storageとAIの実行分を分離。通知を受けただけで追加AIを無制限に起こさない。
条件と注意
公開仕様は対応を確認。本アカウントでのplugin登録可否、実際の購読、質問後の同じjobへの再開、Hubとの往復は未確認。

検証 2位

Slack Events API / Socket Mode

PCから外向きWebSocketで受ける

配送仕様あり・dots受信ゲート未確認

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. 専用Slack会話に保存
  3. Socket受信プログラムがACK・保存
  4. Hub認証 → ローカルAIを起動

復路　ローカルAI → dots → 完了受信

  1. ローカルAIの依頼・回答
  2. chat.postMessage → 同一thread
  3. dotsの受信・再開条件は未確認
  4. 完了 → Slack → Socket受信
利点
公開HTTP入口不要。PCが稼働する小さな試作に向く。Slack会話を人も読める。
弱点
別Bot投稿でdotsが起動するかが最大のゲート。接続refreshと欠落補完が必要。Socketは保存装置ではない。
設定と権限
bridge app、app-level connections:write、参加会話のhistory scope、chat:write。botの会話参加とdotsとの共存。ローカル受信プロセスは常駐。
PC停止と復旧
PC上だけのreceiverは停止中受信不可。再接続＝全件replayの保証は確認できず、履歴との差分照合が必要。cloud receiver＋queueなら停止耐性を追加できる。
費用と負荷
初期は中、常駐PCと再接続運用が必要。Slack契約・app枠・LLM枠は別。API無料／LLM無制限とは断定しない。
条件と注意
Slackのbot event表現は確認。dotsが別Botの本文を依頼として扱うか、mentionなしthread返信の回収、補完可能期間は未確認。

検証 3位

Slack HTTP Events ＋中継

常時受信と永続化をPCから切り離す

配送仕様あり・中継未構築

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. Slack保存 → HTTPS Events
  3. 中継が署名検証・queue保存・ACK
  4. PC受信 → Hub認証 → ローカルAI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIの依頼・回答
  2. chat.postMessage → 同一thread
  3. dots再開はSocket案と同じ未確認
  4. 完了 → 中継保存 → PC受信
利点
PC停止中の受付を維持しやすい。永続queueで受理後の再試行・監査・dead-letterを設計できる。
弱点
HTTPS公開口、署名、ストレージ、監視が増える。Socketから変えてもdotsのbot拒否条件は解決しない。
設定と権限
Slack app/event設定、signing secret管理、中継HTTPS、queueとPC outbound取得。scopeはSocket案と会話種別に応じた同等範囲。
PC停止と復旧
中継受理分を保持し、PC復帰時に取得。Slackの未配送分は別問題。PCへのtunnelだけでは停止耐性は得られない。
費用と負荷
導入・運用は高。queue保持量・egress・監視費とSlack/AI契約が別。低遅延候補だが実測値なし。
条件と注意
HTTPは3秒以内ACK、通常最大3回retry。Delayed Eventsの24時間毎時retryもbest effortで永続保証ではない。

検証 4位

GitHub Webhook

Issue / PR会話を記録の正本にする

配送仕様あり・dotsのevent購読未確認

往路　dots → ローカルAI

  1. dots が質問・停止・完了をcomment
  2. GitHubが保存 → issue_comment
  3. HTTPS中継が検証・queue保存
  4. PC受信 → Hub認証 → ローカルAI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIが依頼・回答comment
  2. GitHub保存 → dots側のevent購読等
  3. dotsの起動・再開は別途必要
  4. 完了comment → webhook → PC
利点
コメントURL・IDが証跡になる。Slackの会話範囲に左右されず、コード案件と対応づけやすい。
弱点
GitHub webhook自体はdotsを起こさない。接続済pluginが対象commentを起動条件にできるか未確認。新規受信口と管理権限も必要。
設定と権限
repo webhook管理権限、またはGitHub App Issues:read購読。comment読書きはIssuesまたはPull requests権限。HTTPS中継、署名secret、10秒以内2xx。
PC停止と復旧
受理済queueとGitHubコメントから復旧。GitHubは失敗配信を自動再送しないため、再配信・差分照合を設計する。
費用と負荷
中～高。中継運用とAPI上限あり。Actionsを中継にする場合は別の実行枠・設計が必要で本案に暗黙追加しない。
条件と注意
issue_commentはPR会話コメントも対象。inline review commentは別event。gh webhook forwardは開発・試験専用でproduction非対応。

検証 5位

GitHub 軽量ポーリング

AIを起こさない小さな差分取得プロセス

差分取得仕様あり・自動往復未確認

往路　dots → ローカルAI

  1. dots が質問・停止・完了comment
  2. GitHubに保存
  3. PCが対象Issueの差分を定期GET
  4. 新しいjobのみ保存 → Hub → AI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIが依頼・回答comment
  2. GitHubに保存
  3. dots側の許可済起動経路が必要
  4. 完了commentを次回GETで回収
利点
公開受信口不要。GitHubに残る履歴からPC復帰後に追いつける。限定された案件では実装が小さい。
弱点
検知は巡回間隔分遅れる。PC側pollだけではdotsを起こせない。削除・非公開化・権限変更で復元できない。
設定と権限
単一Issue/PRのcomments API、最小read/write権限、ETag/If-Modified-Since、ページング、comment IDのwatermark、429/403 backoff。
PC停止と復旧
停止中はGETも実行も不可。復帰後の可視コメントを照合する。編集の扱いと古い未処理jobのTTLを決める。
費用と負荷
初期低、運用中。通常認証5000 requests/h。認証付き304はprimary枠を消費しないがsecondary制限等は残る。
条件と注意
GitHub公式はwebhook優先。これは公開口等を使えない場合の代替。dots側を毎回AI巡回させる設計は採用しない。

根拠：G5 / G6 / G7

検証 6位

Slack 軽量ポーリング

小さな専用会話の補完・代替

取得仕様あり・対象権限とdots受信未確認

往路　dots → ローカルAI

  1. dots の質問・停止・完了
  2. Slack会話とthreadに保存
  3. PCがhistory＋対象repliesをGET
  4. 新しいjobのみ保存 → Hub → AI

復路　ローカルAI → dots → 完了受信

  1. ローカルAIが依頼・回答を投稿
  2. Slack同一threadに保存
  3. dotsの別Bot受信条件は共通
  4. 完了をhistory/repliesで回収
利点
公開受信口やSocket接続維持が不要。既存会話の補完には使いやすい。
弱点
historyだけでは古い親への返信を拾えない。保持期限・app分類・会話数で復旧と遅延が変わる。bot拒否を回避できない。
設定と権限
historyとrepliesの対象を固定し、会話種別のhistory scope＋chat:write。thread_ts・ts・pagination・取得watermarkを保存。
PC停止と復旧
復帰後にアクセス可能で保持中の履歴のみ補完。削除済／保持期限外は復元保証なし。本人とdotsの既存DMを第三Botが読めると仮定しない。
費用と負荷
内部専用appは現行Tier 3（50+回/分）。Marketplace外の新規商用配布等は1回/分・15件の制限対象。method×workspace×appで評価。
条件と注意
対象app分類、tokenでの実際のthread可視性を確認。一律user token必須／全app1回毎分とは断定しない。

C2では最上位から一往復だけ試す

C1では以下を実行しない。本人がC2の外部送信・設定・PC操作・費用を許可した後、専用の合成案件で行う。

  1. plugin・会話・repoの利用条件、PC・Hub・CLI認証・専用cwd・既存承認設定を確認する。
  2. 「色を質問してから合成メモを完了する」というjobを1件だけ送る。
  3. dotsの質問 → bridge保存 → ローカルAIを一度起動 → 固定回答「青」 → dots再開 → 完了の受信・保存を追う。
  4. 同じeventを1回だけ再配送し、追加AI起動・二重回答がないことを確認する。
  5. 一往復のIDと時刻が揃った方式だけC3候補へ渡す。不成立なら理由を残して次点へ進む。

上限案：各候補は合成job最大2件、1件10分。2件目は原因特定後の安全な修正確認だけ。制限値はサービスSLAではなく、ループと費用を抑える実験予算。

共通原因を先に止める。Hub/CLI起動失敗は方式を替えて繰り返さない。Slack bot受信が拒否仕様ならSocket→HTTP→pollと回さない。権限未許可は「条件待ち」で、技術的不成立と分ける。

方式ごとのオーナー操作、最小構成、成功証跡、失敗切り分け、後片付け、次点条件は FINDINGSのC2計画 にまとめた。

候補ごとの最小試験と撤収

具体額は未算定。C2前にオーナーが対象・外部送信・設定・PC操作・支出上限を承認する。公開sampleの導入も自動承認ではない。共通シナリオと上限を各候補へ適用する。

1 MCP Events

最小構成・本人操作・費用：認証MCP＋永続queue＋PC receiver。本人がplugin接続・購読と利用枠を承認。中継compute/storage＋AI費。

成功証跡：discover/list→subscribe→callback検証→dots質問→Hub一回→回答event→dots完了toolを相関。inbox/outboxの保存を別確認。sampleのpoll/SSEで代用しない。

次候補・後片付け：未許可は条件待ち。提供条件不適合は理由を残し2へ。unsubscribe、試験queueと一時権限を許可範囲で撤収。

2 Slack Socket

最小構成・本人操作・費用：専用会話＋Socket receiver＋local inbox。本人が両app参加、connections:write、history/chat、mention利用時app_mentionsを設定。PC＋AI枠。

成功証跡：envelope/event/threadとdots実senderを記録。Bot除外を確認し、対応表だけでなくjob保存を見る。既存sessionのresume案ではTUI/bridgeの書込み担当を一つにする。live TUI続行や文脈なし新規会話を成功にしない。

次候補・後片付け：接続方式だけの障害なら3へ。Bot拒否は3/6も共通なので4へ。receiver停止、一時app権限を撤収。

3 Slack HTTP

最小構成・本人操作・費用：署名HTTPS受信＋queueまたはn8n/DB＋PC outbound取得。本人がURL/署名設定を承認。常時中継・実行数＋AI費。

成功証跡：3秒ACKと保存後処理を分離。許可済みreceiver一時停止中の受理jobを復帰後回収。workflowの再開とdotsの再開を別に記録。

次候補・後片付け：受理前と保存後の障害を分け、解消不可なら4へ。購読/URLを戻し、一時中継・queueを撤収。

4 GitHub Webhook

最小構成・本人操作・費用：専用Issue＋comment読書き＋webhook queue。本人がrepo管理権限とdots側triggerを確認。中継＋AI費。Actions採用は別判断。

成功証跡：delivery/comment/author/job/runを相関。Bot・自発返信の再帰起動を防止。Actionが動いてもdots起動の証拠にしない。

次候補・後片付け：受信口制約なら5へ。dots trigger欠如は5にも共通。webhook停止、試験Issueを記録付きclose。

5 GitHub poll

最小構成・本人操作・費用：対象Issue一つ＋60秒以上の差分GET。本人が限定read/writeとdots側triggerを確認。API上限・PC＋AI費。

成功証跡：ETag/page/watermarkで新commentを取得。空振りAI起動0。comment取得とdots回答後の再開を別に確認。

次候補・後片付け：403/429は条件待ち、設計不成立なら6へ。poller停止、Issue close、不要権限を撤収。

6 Slack poll

最小構成・本人操作・費用：一会話/一thread＋history/replies差分取得。本人が会話可視性・Bot条件・app分類を確認。API上限・保持期間・PC＋AI費。

成功証跡：60秒以上またはRetry-After。古い親への新返信を回収。Bot拒否や不可視DMをtoken切替で回避しない。

次候補・後片付け：保持期限外・不可視は条件/対象を再評価。次は7。poller停止、試験設定を撤収。

7 A2A

最小構成・本人操作・費用：両端の現行Agent Card・認証・binding＋task store。本人がアクセス/capabilityを許可。endpoint/保存＋双方AI費。

成功証跡：同task/contextでinput-required→回答→completedを記録。push利用時はcapabilityとHTTPSを確認。別agentのsample成功は代替不可。

次候補・後片付け：dots側対応がなければ条件待ち/不成立を区別し再評価。task取消・push設定解除・一時endpoint停止。

共通の安全境界と理由ログ

event_id / job_id / sender / threadまたはtask / 保存時刻 / request_id / run_id / reply_id / 完了時刻を相関する。事例ID・source version・resumeの種類・inbox/outbox保存も記録する。秘密は記録しない。入力は信頼できないデータとして扱い、許可済sender・job・cwd・固定promptへ変換してから起動。未処理jobはleaseとTTLで管理し、停止スイッチ・最大run数を設ける。

HTTP受付、dots起動、ローカル起動、回答後の再開、完了確認は別phase。停止通知はblocked等の状態を表し、プロセス強制終了と同一にしない。試験後は購読・poller・一時webhookを停止し、試験データと権限を承認範囲で撤収する。
