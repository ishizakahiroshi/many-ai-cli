# #5 補足：複数方式を比較するC2の試験設計

最終更新: 2026-10-03 JST

## 目的・現在地・変更点

案件は `#5 many-ai-cli dots-bridge-c1-20261003`、対象many-ai-cli、既存develop向けDraft PR #8を継続更新する。提出済みC1追加調査headは `855786ad207a775b145e22725215df24ab9125bd`。このheadのValidate・secret-scan成功をローカル指揮者が確認済み。独立レビュー合格の報告あり。本人は比較HTMLを確認した。全表示項目/スマホQA・接続実験・実機検収は完了扱いにしない。

オーナーの合意により、当初の「順位順に試して最初の成功方式を採用」から変更する。有力複数候補を比較し、主経路と補助/手動復旧経路を選び、複数入口を共通の案件管理・キューへ集約する。第一候補が成功しても比較を終了しない。全7方式を実装・常設する要求ではない。

本依頼はC2の試験設計・役割分担・必要設定・実装指示の具体化まで。原INSTRUCTIONS/REVIEWと追加PUBLIC_RESEARCH指示のうち、方式選定については本補足が新しい方針。実験やコード実装の許可には拡張しない。

## 比較対象と役割

- 最初の二候補はMCP tools＋MCP Events＋永続キュー、Slack Socket Mode。PC停止中の受付を重視する場合やSocket固有制約がある場合はSlack HTTP＋中継も比較に含める。
- GitHubは指示・成果・レビューの記録として評価する。Webhook/pollを起動や復旧に使う実益があれば追加候補にする。記録経路と起動経路を混同しない。
- 未許可・未提供は条件待ち、方式の制約は不成立、片方向成功は部分成立。Bot受理条件が共通ならSlack transportを変えるだけで解決すると仮定しない。
- 主経路と補助経路の共通障害を示す。同じqueue・認証・PC・dots起動条件に依存する二経路は、それらの障害の代替にはならない。

## 許可範囲

公開情報・既存ソース/テストの読み取り、設計文書・比較HTML・既存看板更新、必要な生成索引更新、commit/push、既存Draft PR #8更新、独立文書レビュー。固定指示を改変しない。更新前にremoteを照合し、既存変更と他案件を保護する。

製品/試験コード変更、依存導入、新規plugin/app/webhook作成、認証情報取得/保存、外部試験送信、Hub/CLI起動・再起動、Build、常設監視、C2接続実験、merge/main push/releaseは未許可。必要なものを具体的な追加実装指示として提案し、実施はしない。秘密値・個人PC絶対パス・私用資料を公開文書へ写さない。

## 成果物

このディレクトリにC2_TEST_PLAN.mdを追加し、FINDINGS.mdのC2節、comparison.htmlの選定/試行フロー、PROGRESS.mdを新方針へ揃える。過去の提出/CI履歴は保持する。計画はこの文書だけを読んで担当が動ける粒度にする。

C2_TEST_PLAN.mdへ以下を具体化する。

1. 候補別の最小構成図、常駐場所、受信/保存/起動/返信の担当、公式仕様・ソース証拠と未確認条件。
2. オーナー操作一覧：設定画面への導線、必要scope/権限/契約、対象会話・plugin・repo、各設定が必要な理由。アカウント内の利用可否を公開資料だけで確認できなければ、本人が判定する手順を示す。不要な全件設定を求めない。
3. 実装が必要なら、既存ソース・関連テストを読んで、dots側の変更予定ファイル、ローカル側adapterの接続契約、依存候補と採用理由、正確な検証コマンドを提示する。仮のファイル名/未公開APIを既存機能として書かない。#3 Rust作業に干渉せず、対象ソース基準と稼働版差を記録する。
4. 同じ合成課題で各候補の「依頼→dots質問→受信/保存→ローカルAI起動→回答→dots続行→完了回収」を評価する。成功しても次候補を評価する。実測できない候補の条件待ちと比較限界を記録する。
5. UX比較表：本人の操作回数、質問後の続行、完了回収、遅延、会話の見やすさ、PC停止/再接続の復旧、導入・維持負担、費用。未実測を合格値で埋めない。
6. 複数入口試験：同一報告が二経路から届く、遅延/順序逆転、自己返信ループ、主経路停止、切替後に元経路が復帰、途中クラッシュ。共通job_idとsource eventの相関、inbox/outbox永続化、単一実行/単一書込み、元run状態の照合を合格条件にする。通信ACKだけで完了にしない。
7. live tool待ち/既存session再開/fresh run/dots同job続行を区別。session対応表だけ保存されても待ちjob復旧の合格にしない。Hub routineのactive衝突とrequest_id alias問題を共通ゲートにし、別IDで無制限再試行しない。起動されたAIの認証/コネクタ/cwdを現在の会話から引き継げると仮定しない。
8. 役割別検収表：dotsの自動テスト・独立レビュー、ローカル指揮者の内部テスト・実機一往復・複数入口/復旧検収、本人のアカウント設定・必要な起動・UX/採用判断。親の検収結果をdotsへ返す経路も示す。
9. 試験予算：合成job最大2件/候補・各10分・同event重複1回を基準に理由付きで調整案を示す。必要な金額は根拠と対象プランを示し、本人の支出上限は勝手に決めない。停止・撤収・一時設定の戻し方を具体化する。
10. 採用判断：主経路、補助経路、GitHub記録の役割と共通障害、追加実装の範囲、本人判断が必要な事項を一つの表にまとめる。全候補未成立なら共通原因を切り分ける。

## 暫定運用・セッション引き継ぎ

当面は本人がdotsの返信通知に気付き、ローカルAIへ「#5の進捗を見て」と伝える。本文の転記は不要で、ローカルAIが認可済み経路からSlack/GitHubを取得・照合する。このセッションに自動通知・定期監視・自動起動はまだない。設計の完成だけで稼働済みと表現しない。
