# 外部 AI の停止を看板から追う案

Status: 提案。実装・外部 AI への接続・自動承認は未実施。対象: #48。

## 問題

複数工程を依頼した外部 AI は、サービスが出す操作承認や、次工程を始めるかという会話上の質問で待つことがある。利用者が画面を見続ける代わりに、事前に許可した範囲の仕事を指揮側が続けられるようにする。

## 役割

1. 外部 AI は、できる場合、操作前に看板へ作業 ID、次の操作、対象、状態を記録する。操作後は結果を記録する。
2. 指揮側の見張りは看板を読む。進捗が途絶えても、画面の承認待ちや停止を推測しない。
3. 別の観測手段が実際の画面状態を確認できる場合、承認カード、続行提案、実行中、完了、接続失敗を区別する。看板への事前記録だけでは、画面状態は分からない。
4. 事前に利用者が許可した対象・操作・期限に合い、具体的な操作を確認できる場合だけ対応する。確認不能、対象外、状態が変わった場合は保留し理由を残す。
5. 操作後に実際の結果を確認し、看板へ報告する。成功を観測できない場合は不明として扱い、自動で繰り返さない。

## 重要な未解決点

- 外部 AI が承認待ちで停止すると、看板への書き込みも行えない場合がある。操作前の記録は必要だが、それ自体は停止検出にならない。
- 画面観測と操作を継続実行できる正式な接続・権限は未確認。手動で 1 回押せたことは、常駐監視や公開製品での利用の証明にならない。提供サービスの最新の公式仕様・適用規約を確認し、サポートされない手段の利用を前提にしない。
- 看板の利用者・書き手の権限、外部 AI の実行単位、承認の識別子、元の仕事と対象操作の対応を、既存の契約と実装に照らして確定する。古い表示や別の仕事の承認を押さない。
- ローカル PC が停止すればローカルの見張りも停止する。PC 停止中の対応には別の稼働先と認証経路が必要であり、この案では提供していない。
- タイムアウトは停止の証明ではない。再実行や引き継ぎは実行元の状態を確認できる安全な経路が必要。

## 既存機能との関係

`rust/src/application/board_sync.rs` と `rust/src/hub/board_handoff_routes.rs` は既存の看板連携の調査入口。Iris の保留中 PR の実装や他リポジトリの実行先を、すでに利用できる前提にしない。重複する状態台帳を新設する前に現行の看板・Hub の役割を照合する。

## 実装前の確認と受け入れ

- 看板書き込みが可能な範囲と、承認待ちに入る直前に記録できるかを実測する。
- 実際のサービスの承認カード・次工程の提案・通常の応答・接続断を区別できる、公式に支持される観測経路を確認する。確認できなければ自動操作は未実装として残す。
- 合成の仕事と合成の承認で、範囲内、範囲外、失効、曖昧、重複検出、画面変更、応答なし、停止・再起動を試す。承認された範囲と実行結果を記録する。
- 明示的に許可された実仕事で、事前記録→待ちの検出→対応→結果記録を一周する。会話終了後、Hub 再起動後、PC 停止中を別々に扱い、実施したものだけを受け入れ済みとする。

## 作業順

1. 既存看板・Hub・外部 AI の接続と適用条件を調査する。
2. 識別と記録の契約、待ち状態と許可範囲の扱いを定義する。
3. 合成環境で検知・重複防止・復帰を実装し、検証する。
4. 対応可能と確認した外部サービスで限定実証し、未対応の操作と条件を表示する。

各段階の結果は issue と PR の証拠を正本とし、この文書を進捗台帳として手更新しない。
